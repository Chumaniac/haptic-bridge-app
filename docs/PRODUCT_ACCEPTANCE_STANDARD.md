# Haptic Bridge 完整产品验收标准

版本1，2026-11-05。本文完成验收标准定义，不代表产品已达到标准。当前状态以`acceptance-matrix.json`和验收检查报告为准。

## 验收范围

只覆盖设备所有者本人或明确获授权用户的正常使用。控制码猜测、无授权暴力连接、绕过认证、使用他人令牌或会话均不属于支持功能。没有数字时，允许的产品行为仅是授权范围内的设备发现和所有者确认，不能据此自动取得控制权。

发布前必须冻结明确的品牌/型号/硬件代际/固件/系统/浏览器支持清单。“所有已知厂商”“所有版本”不能作为无边界验收口径。未测型号标为待验证；不支持的能力应明确提示。

## 总判定规则

1. 以下12个门槛全部必需，全部通过才允许宣称完整产品验收通过。
2. 未实现、未运行、缺少证据、受阻、部分通过都按总验收未通过处理。不能用平均分、数量或其他测试的通过抵消。
3. 上游夹具、模拟器、空设备握手、HTTP健康、构建成功与实体设备验收分别记录。软件测试数量不能换算成真实设备覆盖率。
4. 有副作用的检查只在具名授权样机和相应测试环境中进行；没有条件时保持未验收，不搜集公开泄漏的授权信息补齐。
5. 自动检查器只核对门槛和证据一致性，不能认证物理观察、授权真实性或专业安全结论。

## 十二项必需门槛

| 编号 | 验收内容 | 必须达到的结果与证据 |
| --- | --- | --- |
| G01 | 软件基础与依赖互通 | 固定软件版本与来源；上游选定协议/消息/配置测试、本地授权边界和实际组件通信通过，失败/忽略/未运行项如实记录。此项只作为软件基础门槛。 |
| G02 | Central实际程序 | 在声明支持的系统上实际运行Central，验证用户可管理自己的连接；产品与其设备列表、能力、断开及重新连接状态一致。需要程序级回执与授权样机记录，不能用同核心Engine的握手替代。 |
| G03 | Lovense官方授权链路 | 在正常授权条件下完成实际用户旅程；授权取消、到期、撤销、离线和错误身份均有正确结果。只显示获授权范围内的设备。需要具名测试环境和实际设备结果，API示例或成功HTTP响应不够。 |
| G04 | 实际设备功能 | 对每个宣称支持的型号/固件/能力记录期望与实际观察；控制项对应正确设备和功能，空值/边界/重复操作不造成意外动作。不能把命令ACK当作物理动作证明。 |
| G05 | 停止与异常恢复 | 停止和取消能撤销后续输出；断线、关闭、进程异常、权限变化及恢复都有明确结果，旧指令不重放。逐型号观察实际停止；停止未确认时保持受限状态。时间界限依据已确认设备能力设定，不能把0.5秒测试时长当作安全保证。 |
| G06 | 数字码/分享入口 | 只有明确来源与合法授权的代码可被处理；错误、过期、重复、冲突和撤销后的输入不能取得权限。保留前导零；未知来源不向多个厂商散发。未实现时明确拒绝，不能显示成功。需要实际授权与拒绝路径证据。 |
| G07 | 兼容矩阵 | 每个对外支持条目有品牌/型号/硬件/固件/系统/浏览器及测试日期；完整功能与故障场景均完成对应验收。共享协议与品牌名称分开记录。资料条目或合成分流不计实机覆盖。 |
| G08 | 权限和隐私 | 未授权请求被拒绝；控制权限可撤销，设备和用户身份不能串用；敏感信息不进入前端非必要区域、日志、报告、源码或共享材料。本地边界通过不能替代完整厂商授权安全审查；必要的独立复核不得由AI自称签核。 |
| G09 | 性能和资源 | 固定主机、真实设备、场景与负载，记录命令延迟、队列、CPU、RSS、堆、订阅与计时器。队列有上限且停止后清空。完成持续会话与重复连接观察；阈值事先按需求/设备确认，不能事后放宽或把短时RSS增长省略。 |
| G10 | 用户完整旅程 | 正常用户能完成声明范围内的连接/授权、功能使用、状态反馈、停止和结束会话；失败时有可理解的下一步。常驻停止入口可访问，键盘与窄屏可用，模拟和实际环境清晰。真实业务旅程需要实体设备观察。 |
| G11 | 安装与交付 | 干净的声明支持环境可按文档安装启动，不依赖开发者私有目录或凭据；升级/回退保留必要资料、不会重放旧操作。制品可复现，依赖来源、版本、校验及实际分发许可可复核。没有实际发布记录就不写已发布。 |
| G12 | 证据和签核 | 冻结源码版本、制品校验与支持范围；每项证据有用例、环境、期望、实际结果、日期、范围和必要人工确认。实机与厂商流程有明确授权及验收签核；整体未达标时统一保持未通过。 |

## 功能、安全、性能三条验收线

- 功能：每个声明支持条目均覆盖正常、空值/边界、重复、失败/超时、取消/恢复和权限变化。未执行项不能标通过。
- 安全：授权/身份/输入/信任边界优先；缺少授权不能进入有副作用的检查，权限撤销与敏感信息保护要独立验证。
- 性能：缓存、队列、历史、订阅和计时器必须有容量与释放策略；用相同环境的实际观察支持结论，保留CPU与内存的限制和未测项。

每次验收先固定持续观察时长、重复次数、设备数量与可接受延迟；缺少约定时，该性能门槛仍为未完成，不擅自编造厂商安全阈值。

## 最低证据要求

- 软件证据：具名测试回执、组件版本、源码身份、失败/跳过/过滤统计。
- 组件证据：实际运行程序、协商与状态记录，说明是否有真实硬件和副作用。
- 实机证据：每个声明支持条目的现场观察和结果，不存控制码/令牌；由获授权人员确认。
- 授权业务证据：正常授权和拒绝/撤销路径的结果；公开数据、模拟响应或示例令牌不适用。
- 交付证据：候选源码及制品校验、干净环境检查、必要人工验收记录。

## 当前判定

当前真实设备测试数0；Central GUI未验收；Lovense官方API、实际数字配对和分享兑换未实现；现有性能数据属于合成负载或短时本地通信。故完整产品验收应为未通过。

`npm run acceptance:check` 核对既有报告和矩阵，写出本次判定。当前应返回非零状态，这是未达门槛的预期结果，不应改断言或删门槛让它变绿。

检查器当前按已存在的回执映射判断。尚不存在的完整真实流程、交付和签核证据按未验证处理；未来形成具名证据后，应先复核其范围和真实性再更新映射。工具没有“强制通过”选项，状态标签和测试数量不能替代这些证明。

## 从源码检出核对历史材料

执行 `npm run acceptance:check` 会读取验收矩阵，并原子更新 `artifacts/product-acceptance.json`。缺件见 `missingEvidence`，格式损坏的汇总见 `invalidEvidence`。未通过时命令以非零状态结束，仍可阅读这次报告。此操作不会扫描、连接或驱动设备。缺少独立回执时，矩阵里的历史标签不能用于签核当前版本。
